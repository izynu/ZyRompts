# Specification: <feature name>

## Problem

What is wrong or missing today, in one paragraph. Describe the situation, not
the solution.

## Goal

What is true after this work that is not true now. One or two sentences.

## Requirements

Each requirement is numbered and testable. If you cannot write a check for it,
it is a wish, not a requirement.

1. R1 - <observable behaviour>
2. R2 - <observable behaviour>

## Acceptance criteria

The definition of done. Each line maps to a requirement and to a check that can
be run.

- [ ] AC1 (R1): <command or scenario> produces <expected result>
- [ ] AC2 (R2): <command or scenario> produces <expected result>

## Constraints

- Technical: <languages, versions, APIs that must be used>
- Compatibility: <what must keep working>
- Performance: <budget, if any>

## Out of scope

What this change deliberately does not do. Without this section the implementer
will invent scope, and the reviewer will grade against the invention.

## Open questions

Each question names who can answer it and what changes depending on the answer.
A question with no consequence is not blocking; say so and move on.
